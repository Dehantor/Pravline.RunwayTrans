# Баннер главной страницы RunwayTrans

Дата: 13 ноября 2026 года.

## Контекст и решение

Макет описывает первый экран главной, показывает один баннер и допускает от пяти до семи баннеров в ротации. Маршрут `src/app/(frontend)/page.tsx` уже получает язык из запроса и рендерит главную. На нём заменяем верхнюю секцию. Действующие секции перевозок, услуг, грузов, преимуществ, карты, метрик и контакта остаются доступны ниже баннера. Заголовок сайта, подвал и отдельный CMS-маршрут `/home` сохраняют свои обязанности.

Баннер получает упорядоченный типизированный список из 1–7 фоновых изображений и один общий блок с двумя строками заголовка, описанием и одной либо двумя ссылками. При смене фото этот блок сохраняет текст и положение. Сервер выбирает текущий язык из `ru`, `en`, `fr`, `kk`, `zh`. В браузер передаются данные для выбранного языка. Первый экран доступен при исходном серверном рендеринге. Клиентская часть управляет индексом и ротацией. Встроенные ссылки используют префикс языка, чтобы переход на существующую форму `/contacts#callback-form` сохранял якорь.

Изображение подложки масштабируется под первый экран, поверх него расположен равномерный чёрный слой с непрозрачностью 20%. Стрелки листают циклически и получают зелёный фон при наведении. Для одного слайда управление ротацией не выводится. Для нескольких слайдов таймер переключает кадр через 30 секунд и очищается при уходе со страницы. Ротация приостанавливается, пока указатель или фокус находятся внутри баннера, и отключается при системной настройке уменьшенного движения.

## Данные и совместимость

Первый выпуск хранит содержимое в типизированном конфиге репозитория. Стартовый набор содержит два кадра для работающего листания. Первый воспроизводит текст и композицию макета с воссозданным фоновым изображением. Второй использует существующую фотографию техники `public/media/image-2.png`. Дополнительные фотографии добавляются при наличии утверждённых материалов. Это сохраняет работу главной без опубликованного документа Payload и не меняет существующие правила доступа. Переиспользование Pages Hero связало бы стартовый баннер с другим маршрутом и с полями без подходящей структуры повторяющихся локализованных карточек.

Если редакторам понадобится менять баннеры без выпуска кода, решение пересматривается. Тогда модель Payload должна содержать упорядоченный массив до семи элементов, публичное чтение опубликованного содержимого и запись по действующим ролям контент-редакторов. Схема PostgreSQL требует штатной миграции Payload и согласования с общим правилом проекта о создании миграционных файлов. Текущий репозиторий использует Next.js 16.2.3, React 19.2.4 и Payload 3.82.1 с PostgreSQL. [Границы серверных и клиентских компонентов Next.js](https://nextjs.org/docs/app/getting-started/server-and-client-components), [миграции Payload](https://payloadcms.com/docs/database/migrations).

## Проверка и рост нагрузки

- Прямой переход на языковую главную показывает верхний баннер и существующие блоки ниже. Проверить desktop и mobile, светлую и тёмную темы, длинные строки, фокус, наведение и перекрытия.
- При 2 и 7 слайдах проверить ручной переход через край списка, автоматический переход через 30 секунд, паузу при наведении и фокусе. Проверить целевые страницы действий и переход к форме с якорем. При одном слайде отсутствуют недействующие контролы.
- Число элементов ограничено семью по заданию. Пагинация, фильтрация и новые запросы к базе не нужны. Сеть при первом открытии должна загружать изображение первого кадра. Остальные фоновые изображения загружаются по мере показа.
- При росте посещаемости главное влияние баннера на сеть определяется весом фоновых изображений и попаданием в кеш. Если требуется подтвердить готовность к нагрузке, на тестовом окружении сравнить контрольную главную и версию с баннером при 10 запросах в секунду в течение 5 минут. Этот сценарий принят как допущение, измерения должны включать HTTP-ошибки, p95 ответа, объём изображений при первом открытии и повторную загрузку из кеша. Нагрузочная готовность требует отдельного прогона.
